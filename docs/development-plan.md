## 执行原则

- **设备操作全自动。** 打开应用、切换页面、点击、滚屏、截图、读取节点、写入系统设置全部由 adb、抖音采集服务、无障碍动作与识别结果驱动；执行过程不要求用户点按、登录、确认或观察。确实需要授权的项目由 shell 权限直接写入，并在验收记录写明写入的命令、修改前后的值与影响。
- **真实资料优先。** 订单、运单、轨迹和页面文本来自真实账号与真实页面；缺少样本时记录缺少条件并保持未完成，不构造订单、凭据或响应。
- **会话恢复按平台能力选择路径。** 平台提供免密授权（本机已登录的原生 App 授权跳转）时走授权；只提供短信验证码时由通知栏文本取得验证码并自动填入；两条路径都不可用时，改用该平台原生页面的只读采集，不保存也不猜测用户凭据。
- **先回归再扩展。** 修改公共流程前先运行受影响的既有测试，再增加新场景；每次设备执行前记录安装包指纹与数据库状态。
- **职责边界保持。** 平台读取与识别结果解析在平台层；业务写入、包裹合并与事务在 LogisticsRepository；账号锁、批次、期限与恢复在 SyncCoordinator。
- **证据与隐私。** 完整账号、订单、运单、地址与识别正文保存在本机忽略目录；公开仓库只保留源码、测试、公开文档与主 APK。
- **Pinky 任务与验收隔离。** 开发期页面探索与失败诊断可以使用[Pinky](pinky-workflow.md)的 MCP 手机操作工具；Pinky 任务与 instrument 测试、生产采集串行执行，读屏记录只保存在本机 `work/evidence/pinky/`，不作为验收证据。

## S1：抖音物流自动导入闭环

**输入**：真实抖音 App 登录状态、已导入订单 6918361666413145327（当前物流页显示 中通快递 76988792340533、已签收、五条轨迹）、账号抖音号 858740830、现有 DouyinCaptureService、NativePaginationRunner、NativeLogisticsImportSession、DouyinOcrLogistics 与 LogisticsRepository.ingestNativeLogistics。截图识别样本（韵达快递 321371002676018）来自另一页面状态，保留为本机解析测试资料。

**目标**：打开抖音后在首页进入商城与我的订单，按商品标题在订单列表定位已导入订单的卡片，点卡片“更多”，从弹窗点“查看物流”，读取运单、承运商、状态与轨迹并写入生产库；全过程无人工点按。

**工作**：

1. 服务启用与状态：用 adb 把采集服务加入 enabled_accessibility_services，记录修改前后列表；启动抖音并确认服务连接状态为已连接。
2. 订单入口：首页直接点“商城”，再点“我的订单”，选择“全部”。已绑定账号使用数据库保存的抖音号，跳过“我”页；首次绑定的账号仍核对“我”页。
3. 卡片入口：按数据库商品标题定位已导入订单的卡片；点击卡片“更多”，弹窗“查看物流”是独立窗口，按全部可读窗口查找并点击其范围；列表不在顶部时在列表范围内注入向下滑动手势。未导入订单继续进入详情读取订单号。
4. 物流页读取：点击“查看更多物流信息”，逐条展开正文，节点与截图识别结果按时间合并去重；截图识别加入 8 秒超时。
5. 写入生产：按订单编号关联已有订单，调用 LogisticsRepository.ingestNativeLogistics 写入 Shipment、TrackingEvent 与 SourceRef，识别正文与动作写入本机证据目录。
6. 失败暴露与边界：定位失败抛出带页面名称与识别行数的错误，账号置为 PARTIAL；可点击目标只允许“更多”“查看物流”“查看更多物流信息”“展开”等读取入口，交易类按钮继续拒绝。

**完成条件**：一轮执行后生产库出现该订单的运单与全部可识别轨迹，截图与识别正文保存在证据目录；同一订单再执行一轮不产生重复运单与重复轨迹；执行过程没有人工点按。2026-11-25 已满足：两轮分别 33.826 秒与 113.575 秒完成目标导入，轨迹 5 条，重复 0。

**验证**：四项 Gradle 命令；两轮真实设备执行；执行前后数据库比较；证据目录与识别正文；无障碍与前台页面记录。

**影响与代价**：列表直达依赖数据库中保存的商品标题，只对已导入订单生效；新订单仍需要进入详情读取订单号。弹窗与列表使用窗口节点和范围手势，页面结构变化时错误会指出具体步骤。收益是抖音物流读取从八分钟期限缩短到一分钟内完成，后续平台可以复用同一套动作与识别组件。

## S2：抖音完整订单范围与物流历史

**2026-11-26 状态**：已导入订单按商城订单列表卡片“更多”→“查看物流”读取，两轮 42.058 秒与 45.085 秒通过，orders 3、Shipment 3、TrackingEvent 15，两轮表稳定；列表结束标志、全部标签选中状态与未导入订单直接物流保持未完成，记录为 PARTIAL。Pinky 复核记录见 work/evidence/pinky/S2/20261126-0952-pinky-observations.md。

**输入**：S1 的执行记录、真实在途与多包裹订单、抖音列表的滚动能力与结束标志。

**目标**：补齐列表结束、“全部”标签选中状态、候选缺失字段、完整物流历史与两轮一致性。

**工作**：

1. 列表与结束：按列表容器的滚动动作逐屏读取，记录平台明确结束标志（九种文本）的出现位置；没有结束标志时保持 PARTIAL 并写明已读取屏数与末屏节点数。
2. 标签与范围：确认“全部”标签的选中状态在节点属性或页面文本中的体现，取不到时把范围选择标为 blocked 并写明取不到的字段名。
3. 候选字段：对缺少含年份下单时间或配送依据的候选，读取详情页全部字段名与值写入阶段记录，用真实字段决定导入或排除。
4. 物流历史：对每一笔有物流的订单执行 S1 的展开与二次识别，记录轨迹条数、跨年依据与多包裹关系；一个订单多个包裹时保持未关联，不把轨迹并入其他包裹。
5. 两轮一致：同一账号连续执行两轮，比较订单、包裹、来源与轨迹数量。

**完成条件**：列表结束有页面证据或明确的 PARTIAL 原因；每笔导入订单都有真实订单编号、下单时间与配送依据；两轮不增加重复记录；完整轨迹有识别原文。

**验证**：四项 Gradle 命令；两轮真实执行；独立数据库副本比较；证据目录。

**影响与代价**：需要多次真实执行与较长的页面停留时间；滚动与识别的稳定性依赖抖音页面结构，结构变化时错误信息会指出具体页面与缺失字段。收益是导入范围与物流完整性有可核查依据。
