## 执行原则

- **每次只执行一个阶段。** 由用户指定 P0 至 P7 中的一项；完成条件、验证命令和阶段记录齐备后结束当次执行，不自动进入下一阶段。
- **真实资料优先。** 使用现有账号、profile、真实响应、真实节点和真实服务；缺少样本时记录缺少条件并保持未完成。禁止构造订单、凭据、响应或通过绕过流程制造通过结果。
- **先回归再扩展。** P0 没有完成设备回归，不进入平台阶段；后续阶段修改公共流程时，先运行受影响的既有测试，再增加新场景。
- **保持职责边界。** 平台适配器负责读取与解析；LogisticsRepository 负责事务、排除清理和包裹合并；SyncCoordinator 负责账号锁、批次、期限、进度与恢复。页面与适配器使用现有入口。
- **公开接口与 schema 变化需要单独说明。** Room schema、平台接口、业务 Models、凭据格式或签名的变化，必须在阶段记录中写明用途、兼容要求和迁移路径；没有明确需要，保持 schema v2。
- **数据保护。** 破坏性验证使用独立数据库名称和独立副本；开始前保存一致副本，结束后逐字段比较八张业务表和 settings、encrypted_credentials、webview_profiles、work_schedules 四份配置。主库只读核查单独记录。
- **证据与隐私。** 完整账号、订单、运单、地址和采集正文保存在本机忽略目录；公开仓库只包含源码、测试、公开文档和主 APK。普通日志和公开文档只保留必要结果。

## P2：原生采集资源、恢复语义与进度重建

**输入**：T13 的进度文件、采集证据、T14 的数据库与配置副本、当前设备。**目标**：让采集证据有容量边界；恢复采集能够给出完成或明确未完成的结果；损坏进度可以重建；停止、到期和移除路径不再抛出未捕获异常。

**工作**：

1. 证据保留：生产路径保留 NativeSyncProgress 和汇总记录；完整 scan、action、timing 只在诊断开关打开时写入；生产保留最近 3 轮，超过 7 天的自动删除；去掉采集热路径上的 PlatformRegistry.rememberCapture；为账号移除、启动和采集结束增加清理；记录单轮文件数、字节数和耗时。
2. 轮次语义：NativeSyncProgressStore.begin 在 resume 时清空本轮 blockedCards，把上一轮 blocker 保存到诊断字段；新一轮结束后把没有再出现的订单标成 stale 并记录原因；complete 只要求本轮订单 finished 或 stale；blockedCards 的 key 带 cycleId。用一条恢复用例覆盖“上一轮 blocked、下一轮未再出现”的场景。
3. 进度重建：为损坏、版本不兼容或账号不一致的进度增加“重建采集进度”入口；重建前把原文件改名为 .corrupt-时间戳 并保留，重建后清空内存状态并提示“本轮从新的采集开始”。入口放在采集页面的错误状态旁，需要确认对话框。
4. 异常边界：captureRefreshed 使用 AppFailure 表达“采集已经停止”；startOrders 的采集协程捕获 Throwable，CancellationException 继续抛出；onFinished 的证据写入放到 Dispatchers.IO，把 IOException 包成 AppFailure；DouyinCaptureActivity 的入口捕获 AppFailure 并显示在状态文本中。补充停止、八分钟到期、账号移除三种条件的测试。

**完成条件**：单轮采集的文件数量和字节数有记录，旧证据按保留规则清理；恢复后不会永久停在 PARTIAL，完成或未完成都有明确原因；损坏进度可以在确认后重建，原文件保留；停止、到期、移除路径得到 PARTIAL 或明确的配置错误，没有未捕获异常。

**验证**：四项 Gradle 命令；进度与证据目录的前后比较；恢复用例；停止、到期、移除测试；数据库与配置审计；单轮资源统计。

**影响与代价**：改动原生采集的状态管理与证据写入，代码变更集中在 DouyinCaptureService、NativeSyncProgress 和 NativePaginationRunner；需要一次设备会话。收益是长期使用的存储与恢复可靠性，减少偶发崩溃和“永远 PARTIAL”的状态。

## P5：数据保留、系统调度与账号移除

**输入**：真实共享来源、别名、历史非空备注和归档副本，原生进度文件，WorkManager 调度记录。**目标**：补齐迁移与清理分支、系统调度和账号移除的证据。

**工作**：

1. 迁移与清理：用真实副本验证共享来源、别名、非空历史备注和归档的迁移；验证被删除平台的来源清理、账号停用和移除期间的业务保持；确认共享包裹仍有其他来源时保留，独立包裹才删除。
2. 系统调度：用 dumpsys jobscheduler 核查 30 分钟后台更新的实际登记、约束和取消；验证关闭后台更新后任务被取消；验证账号移除后对应任务不再执行；记录系统实际调度与 WorkManager 记录的差异。
3. 进度与移除：验证进度密文损坏、版本不兼容和重建入口；验证账号移除时凭据、profile、原生进度和采集证据的清理；确认移除后主库业务记录保留，其他账号不受影响。
4. 副本审计：开始前保存一致副本，结束后逐字段比较八张业务表和四份应用配置；主库只读核查单独记录。

**完成条件**：独立副本逐字段比较通过；业务提交与恢复标记一致；其他来源和用户字段保持；调度与移除行为有系统侧证据；没有 orphan 查询项、别名或进度文件。

**验证**：四项 Gradle 命令；数据库审计；dumpsys jobscheduler；账号移除与恢复测试；独立副本比较。

**影响与代价**：需要历史样本和系统调度时间，独立副本需要额外保存空间；某些分支可能因缺少被删除平台的来源而保持未完成。收益是数据保留与恢复的证据更完整。

## P6：页面覆盖与 Jev 效果对照

**输入**：真实取件码、未关联抖音订单、外部平台入口、MainActivity 启动条件；按采集会话划分的独立验收资料。**目标**：补齐页面与启动联合流程，量化 Jev 辅助判断的价值与成本。

**工作**：

1. 页面覆盖：验证取件码复制、未关联抖音订单卡片、外部平台导航、MainActivity 启动与自动同步的联合流程；确认生产页面与数据库一致，空结果、筛选、详情、返回和页面重建正常。
2. Jev 对照：使用相同真实输入，比较修正后的程序规则与 Jev 辅助判断的正确性、总耗时、人工介入和费用；记录每条判断的概率、接受结果、人工复核和费用；没有同条件比较时，只报告本次结果，不声明整体提速。
3. 费用与隐私：记录请求数、缓存数、输入输出 tokens 和费用估算；确认发送内容只包含公共标签与必要结构，完整账号、订单、运单、地址和凭据不进入请求。

**完成条件**：生产页面与数据库一致；交易操作全部拒绝；Jev 只在至少 0.95 概率且通过程序检查时采用；相同条件下的比较结果可以复核；费用与隐私记录完整。

**验证**：四项 Gradle 命令；真实设备页面测试；MainActivity 启动测试；Jev 请求与响应记录；费用统计；页面与数据库对照。

**影响与代价**：需要真实样本、重复验证和联网费用；Jev 对照可能因为输入差异无法形成同条件比较，此时保持未完成。收益是补足页面验收并给出模型价值的直接依据。

## P7：发布签名、版本、文档与清理

**输入**：P0 至 P6 的完成状态，用户保管的 release keystore，当前源码与 APK。**目标**：形成可长期安装的发布包，更新版本与已知限制，清理未使用代码与过期文档。

**工作**：

1. 发布签名：生成 release keystore，配置 signingConfigs 与 release buildType；决定是否启用 R8，先用真实页面与平台流程验证混淆后的包；保存 keystore、密码和证书指纹到本机，不进入仓库。
2. 版本与说明：更新 versionCode、versionName、变更说明和 README；记录主 APK 的 SHA-256、签名证书和安装指纹；在 GitHub 创建开发预发布或正式发布。
3. 文档与清理：更新验收记录、项目地图、CodeGraph 记录和已知限制；清理 CredentialStore.deleteServiceSecrets 等旧功能留下的未使用代码；确认没有私人资料进入公开仓库。
4. 最终核查：四项构建检查、主机测试、Lint、安装与覆盖安装、数据库保持、签名与 SHA-256。

**完成条件**：release APK 可以覆盖安装并保留数据；四项构建检查和主机测试通过；README 与实际能力一致；仓库不含私人资料；keystore 已备份。

**验证**：assembleRelease；apksigner 校验；安装与覆盖安装；数据库比较；SHA-256；Git 与公开文件检查。

**影响与代价**：keystore 需要用户保管，丢失后无法用同一签名升级；R8 可能暴露反射或序列化问题，需要设备回归。收益是稳定的安装包与可追溯的发布记录。
